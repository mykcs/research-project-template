# 正式发布、Git 同步与回滚

GitHub main 是源码权威，服务器 published 是已验收运行快照，两者是独立状态。当前尚未配置发布程序及管理员权限；在团队同意前，不改变现有共享目录。

未来由管理员确定发布维护者和服务身份，从明确的 main commit 构建独立版本候选；运行必要测试、环境检查、资源及资产验证。记录源码 commit、真实环境版本、发布者、验证证据和发布时间，确认后在同一文件系统原子替换 current 入口。禁止直接在现役 current 快照执行 git pull。维护者需要核验目标、权限和新旧版本，回滚仅切换至已验证版本；旧版本是否清理须核对运行引用、科研保留和管理权限。

正在运行的实验必须固定其启动时的实际源码与实际环境路径。run.sh 先解析真实项目根目录；项目实验的子进程和资产路径也需遵守该原则。脚本不等于管理员级隔离或完整发布器。

试点采用手动维护者发布记录；协商完成后再通过受控流程实现 main 合并 → 独立候选 → 检查 → 发布 → 切换 current → 记录结果。未验证的候选不能切换。自动同步不能绕过科研验收。当前无任何自动服务器发布。

## 跨仓集成和交付包（适用时）

独立科研任务成熟后可以建立组合入口，固定经过验证的上游 commit/版本（例如 Git submodule、锁定依赖或发布清单），由独立 PR 更新并进行接口与端到端验证；不要自动追踪各上游 main。迁移/交付包应说明包含与刻意不包含的内容、所需外部依赖/资产及版本、校验标识、目标环境和启动验证。大型数据/模型不默认进入 Git，必须遵守实际访问及许可；交付包静态存在不等于运行成功。

启动器在公共运行模式下固定实际 Python 所在目录，同时保留解释器最终链接，以避免丢失虚拟环境语义。实际共享环境跨账号和原生仿真仍需独立验证；软件测试只覆盖路径处理与入口边界。
