# 科研项目仓库、协作开发与实验交接规范 V0.5（三种仓库形态）

**状态：团队协商稿。** 先在导航、抱箱行走等科研项目试点。现阶段依靠成员自觉遵守，不实施新增权限控制、公共环境更换或自动发布。现有安全约束继续有效。待协议完善并获得团队共识后，由管理员实施。

## 1. 规范分级：强制结果与最小统一结构

本规范以能否完成真实交接、协作和复现为准，除第 3 节明确的 `src/` 和 `website/` 结构要求外，不以文件数量、目录命名或工具是否完全一致评分。

- **必需（MUST）**：交接需要的信息、可执行能力、安全边界或证据必须具备。可以使用现有文档、等价文件、项目现有工具或可访问链接实现；除第 3 节的强制源码与网站位置外，不要求照搬模板目录。
- **条件必需（MUST IF）**：只有相关情况存在时才必须提供，例如使用 GPU 则记录 GPU 资源，依赖共享环境则说明版本和隔离方式。条件不适用时简述原因；适用但未确认的内容标记未知或阻塞，不能以 N/A 掩盖。
- **推荐（SHOULD）**：默认采用模板的文件组织、工具与实践；有成熟现有方案时可直接复用。只需保证相同内容与功能可发现、可使用，不要求提交偏离审批或空文件。
- **可选（MAY）**：有实际需求才建立；缺少这些内容不构成交接失败。
- **未来建议（PROPOSED）**：需团队与管理员达成共识后实施，目前不能当作已生效的强制制度。

同一信息只维护一处权威来源，其他入口链接即可。已有项目按第 3 节实际形态，将非网站业务源码归入 `src/`、综合项目附属网站归入 `website/`；独立网站仓可直接使用根 `src/` 或 `website/` 子树；通过最小迁移保留原有行为，无需为其余目录匹配而重写正常工作的代码。新项目推荐直接使用模板，但可以根据规模合并、拆分或省略非必需文件。

## 2. 交接必须具备的内容

| 内容 | 级别 | 验收重点（文件位置可替代） |
| --- | --- | --- |
| 仓库形态与范围 | MUST | 说明独立 Code、独立 Website 或综合 Project 的实际范围、源码及入口；README 形态标记为推荐格式 |
| 非网站业务源码位置 | MUST IF | 有现行自有非网站业务代码时，实际可运行源码位于根 `src/`；检查路径、导入和发布，不以空目录或软链接代替 |
| 网站源码与构建 | MUST IF | 综合项目附属网站位于 `website/`；独立网站使用根 `src/` 或 `website/` 子树；记录构建、预览、发布及访问范围，无网站不建空目录 |
| 新人入口 | MUST | 能找到目标、上游关系、现状、运行方式、重要文档及维护/反馈渠道；通常使用 README |
| 任务关系 | MUST | 上游任务或独立项目说明、主线目标、验收、当前未完成事项；子任务和依赖在确实存在时记录 |
| 可执行运行与复现 | MUST | 真实命令、工作目录、前置条件、预期输出；没有成功实验时明确记录并提供当前可运行检查或失败复现入口 |
| Dev 开发环境 | MUST | 依赖、版本、个人开发方法、检查与 CI 合同、协作方式；服务器资源、公共环境及发布信息按实际适用 |
| 资源信息 | MUST IF | 计算需求、GPU/CPU、显存、RAM、磁盘、耗时与预算；区分估计、实测、未知 |
| 实验结果与证据 | MUST IF | 已声明结果的可追溯运行条件、指标、失败/未验证边界及复现证据 |
| 关键接口与假设 | MUST IF | 接手或集成必须了解的算法、坐标系、单位、模块接口、限制和关键决策 |
| 交接状态 | MUST | 已完成、未完成、阻碍、下一步及接手人员独立验证结果 |
| AI 开发约束 | MUST IF | 使用 AI 辅助开发时提供可发现的项目规则和必要贡献记录；AGENTS.md 是推荐入口 |

以上是交接最低内容，不要求逐项建立独立 Markdown。规模较小的项目可以在 README 或现有文档中集中说明。完整交接要求接手者实际验证；仅填写文档不能证明交接通过。若真实实验或运行条件仍有阻碍，应明确交付边界，不虚构成功。

## 3. 强制目录、推荐结构与可选扩展

### 3.1 三种合法仓库形态（MAY）

同一模板允许以下三种组织形式，均为正式支持的选择，而不是三个模板仓库。

| 形态 | 所拥有的内容 | 源码及构建边界 |
| --- | --- | --- |
| Code（独立代码仓） | 科研、算法、工具、库等非网站业务代码；可链接独立网站 | 根 `src/`；无附属网站不要求 `website/` |
| Website（独立网站仓） | 网站或 Web 产品自身；可有站点 API、数据和文档，不必有科研算法 | 默认根 `src/`，构建配置与资源随站点；也允许 `website/` 子树作为站点的唯一构建根（可有内部子目录） |
| Project（综合项目仓） | 同一项目的非网站业务代码、网站与相关产物 | 根 `src/` + 根 `website/`，各自依赖、检查、运行及发布入口 |

**MUST**：声明仓库实际职责与构建入口。**SHOULD**：在 README 增加一行 `Repository profile: code`、`Repository profile: website` 或 `Repository profile: project`，供轻量检查使用；不用为标记另建配置文件。网站本身是独立产品时，其服务端代码属于站点，不因使用 Python 或 API 而自动认定为综合科研仓。

**SHOULD**：以项目/产品边界而非技术栈分仓。新项目同时拥有研究代码和展示网站时优先综合 Project；访问权限、独立产品身份、维护责任或发布生命周期确有区别时允许独立 Code / Website，现有成熟分仓亦可保持，不要求为规范盲目合仓或拆仓。跨仓时记录权威来源、链接、必要接口和适用的版本；同仓时网站构建上下文只包含获准内容，目录隔离不是权限隔离。合并代码不代表授权部署网站。

### 3.2 条件必需目录与推荐扩展

- Task：建议维护上游、主线、当前、交接及子任务；历史任务较多时再建立归档。
- Dev：建议集中维护环境、资源、协作、CI 与发布；文件可以合并，现有权威文档可直接引用。
- Design：建议保存架构、接口和关键技术理由；正式 ADR 系统不是必需。
- Experiments：建议索引实验记录；可使用现有实验管理系统或可访问的证据位置。
- Wish：可选；未立项目标较多时建立，不能替代 Task。
- References / 资料参考 / 文献资源库：可选。机器人导航、抱箱行走以及其他科研项目都不要求单独建立参考资料目录、论文清单或网站资源库；不以参考资料数量验收交接。具体实验结论的必要证据、关键外部依赖来源、引用义务和许可证仍需按实际情况保留。
- **`src/`（MUST IF）**：若维护非网站业务代码，所有现行自有业务源码（算法、控制、任务模块、库及运行实现）位于根目录 `src/`，内部包结构按项目设计。禁止根目录平行维护同一实现、空目录或符号链接伪装。启动/辅助脚本、配置、测试、文档、外部依赖与不可变历史实验快照可保留各自职责目录；不得在这些目录新增现行研究业务实现以规避规则。历史证据保存原路径及哈希。迁移保留原运行语义；确需兼容旧入口时只保留委派层，并明确退役或兼容范围。
- **`website/`（MUST IF）**：综合项目同时维护非网站业务代码及附属网站时，网站源码、框架配置、依赖定义及锁、静态资源集中于 `website/`（例如 `website/src/`、`website/public/`），不与科研代码混放。独立 Website 仓可采用根 `src/`（SHOULD）或一个实际的 `website/` 子树（MAY），不要求额外研究源码。网站存在时 README 指明构建、预览、部署配置和访问范围，适用 CI 验证真实构建根；网站内容仅引用已获授权的科研数据，不自动发布。无网站不创建空目录。
- configs、scripts、tests、run.sh：推荐默认形式；采用其他等价结构、构建工具或启动方式即可。

## 4. 协作与权限

正式源码来自组织 main，成员 clone 至自己的 Home，以功能分支开发、测试、PR、审阅、合并；Fork 不是前提。暂不能强制主分支保护时按团队约定执行，未来由组织管理员核对套餐并配置。旧共享目录不直接覆盖。

安全与协作边界不得因为文件结构可替代而放松。不得擅自写入其他成员工作区、公共环境、现役共享版本或变更服务器配置，不得抢占他人资源；现有权限规则仍有效。/home/shared/<repo>-published 未来由管理员设置普通成员只读、可执行，指定维护者受控写入，和 Git main 通过验收后的发布流程同步；现阶段不修改权限，仅凭自觉。服务器管理权、公共环境和资产同样采用未来最小权限原则，不擅自收回现有权限。见 [Dev](README.md#服务器协作发布与回滚)。

## AI 辅助开发与多人协作

**个人开发，积极发挥 Agent 的能力；多人协作，提交和合并前加强检查与审阅。** 鼓励成员在个人工作区充分利用 Agent 调研、实现、测试与改进，提高科研效率。涉及团队共同维护的代码、接口、配置及科研结论时，提交者应先理解并检查实际改动、测试结果及影响范围，再提交 PR；合并前应进行与风险相称的审阅，尤其关注兼容性、对其他成员工作的影响及科研证据。必要时邀请相关同学交叉审阅。不将 AI 生成或 CI 通过视为人工理解与审阅的替代，也不把普通个人开发变成逐步审批流程。现阶段依靠团队自觉执行，审阅方式和强制门槛待团队协商。

## 5. 环境、资源、启动与 CI

必须提供真实可执行的运行和检查方法、依赖版本或可复现环境标识。Python 项目推荐 uv、pyproject.toml、uv.lock、Python 版本声明和 Ruff，允许等价成熟工具。已有项目可使用 Makefile、现有脚本或平台运行入口，不强制 run.sh 或指定子命令名。本模板的 Code 示例提供 bootstrap/doctor/smoke/audit/reproduce/test/lint/ci；真实实验入口须实测，模板未配置时明确失败。独立 Website 使用真实网站依赖、构建和测试命令替换 Python 示例，不强制 Python/uv、run.sh 或科研实验。综合 Project 分别记录代码和网站的验证合同。

若使用共享大型仿真底座，应版本化并与任务代码、个人开发环境隔离；个人安装绝不写入公共环境，公共运行不自动同步依赖。资源需求区分实际测量与估计，未知标待测。见 [Dev 环境与资源](README.md#环境与资源)。

Dev 必须说明 CI/验证合同、必需检查、执行入口、实际启用状态以及证据。适用的依赖一致性、静态检查、格式、测试、软件 smoke 等应覆盖；工具及托管平台可替代，托管 CI 不要求强制采用，不能把未运行说成通过。原生科研验收与低成本 CPU CI 分开；按真实任务风险确定门槛。见 [Dev CI](README.md#ci)。

## 组织现有实践的可复用原则（按项目适用）

- **条件必需：接口契约与兼容性。** 多人依赖的 API、机器人状态/动作、数据格式等应明确维度、顺序、单位、坐标系、时间、版本及失败语义，并有针对关键契约的可运行检查。复用稳定核心接口；后端不支持的能力不得静默忽略。实机、Mock、运动学及动力学边界明确。
- **条件必需：科研证据。** 实际运行、数据转换、对照评测和部署须记录真实输入与版本、关键参数及评价范围；短跑、抽样、模拟或历史回放不得替代正式结果。可采用机器可读收据与输入指纹，但格式不强制。
- **条件必需：外部依赖与集成。** 依赖跨仓代码、模型或大型资产时，记录可追溯版本、兼容性、获取方式和使用许可；集成发布固定实际已验证版本，不默认跟踪各上游最新 main。
- **推荐：轻量入口与分层验证。** 公共逻辑只维护一处，命令入口复用公共实现。预检/只读观察、软件测试、原生仿真和硬件动作分层；按实际风险验证超时、停止、错误输入及资源清理。既有旧入口或历史实验明确标识而非盲目删除。
- **可选：多基线与组合仓。** 多模型依赖冲突时，使用独立环境和共享稳定接口；确需集成多个独立项目时，采用已验证的 commit 固定、Git submodule 或其他可复现集成方式，不强制建立新仓库或子模块。
- **条件必需：交付包边界。** 迁移、发布或共享外部工件时明确包含/不包含内容、依赖版本和获取方式，记录必要校验及运行验收；不把文件存在或静态校验当成复现通过。

这些原则是对工程能力与验证质量的要求，不强制建立资料参考库、基线目录、集成仓、ADR 或其他固定结构。具体项目按实际适用范围落地。

## 6. 验收与交接

科研证据记录实际 commit、环境、资产、配置、种子（适用时）、Run ID、真实运行条件、指标及失败结果。区分 Mock、CPU、MuJoCo、PhysX 和实机；规划成功不等于导航成功，抓取成功不等于负载行走成功，端到端必须按任务合同验证同一连续过程。接手者能独立读懂现状、定位资源、运行检查、复现声明成果（无成功则明确未成功）、在个人工作区修改、测试和提交 PR。科研未完成也可诚实交接。AI 重要贡献应有真实溯源和验证依据。

验收按必需及适用的条件必需项判定，按声明形态核查实际 `src/` 与适用的 `website/` 源码位置及迁移后运行；不检查所有建议文件是否存在。交接验收入口见 [Task/HANDOFF](../task/HANDOFF.md)。

## 7. 后续协商

明确维护者、权限、公共环境与模型资产范围、GPU 使用、分支保护、CI 配额、原生科研门槛及 Git 同步发布机制。先完成两个项目实际交接，反馈再迭代。本文件不声明团队已认可或服务器已实施。

## 科研方法与公共 CI 资源

科研型项目按需明确研究问题、可证伪假设、基线、对照与实验协议、证据和结论局限；既有研究记录可以承载这些内容，不强制目录。见 [Research](../research/README.md)。组织 CI 属于团队共享预算；高频开发优先个人资源，合并验收按需使用组织 CI。默认不公开部署或上传私有资产，不擅自改变计费、权限与运行环境。
