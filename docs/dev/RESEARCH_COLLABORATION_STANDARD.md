# 科研项目仓库、协作开发与实验交接规范 V0.2

**状态：团队协商稿。** 先在导航、抱箱行走等科研项目试点。现阶段依靠成员自觉遵守，不实施新增权限控制、公共环境更换或自动发布。现有安全约束继续有效。待协议完善并获得团队共识后，由管理员实施。

## 目标与仓库

一个独立主线任务原则上一个仓库；成熟后按接口统一集成。README 是新人入口，应具备真实目标、上游任务、现状、代表性结果、环境与资源、可执行命令、文档入口、负责人和交接方式。使用仓库中真实文件及运行入口，不为形式统一破坏已有项目。

Task 管理上游、主线、当前、交接、子任务与归档；主线明确非目标及最终验收。Design 管理系统架构、接口、技术理由与 ADR；Wish 管理未来未立项目标；Experiments 管理科学证据。每个子任务有编号、目标、依赖、验收、负责人和状态，已完成及时归档。Dev 是开发环境、资源、协作、CI、发布规则的入口。

## 协作与权限

正式源码来自组织 main，成员 clone 至自己的 Home，以功能分支开发、测试、PR、审阅、合并；Fork 不是前提。暂不能强制主分支保护时按团队约定执行，未来由组织管理员核对套餐并配置。旧共享目录不直接覆盖。/home/shared/<repo>-published 未来由管理员设置普通成员只读、可执行，指定维护者受控写入，和 Git main 通过验收后的发布流程同步；现阶段不修改权限，仅凭自觉。服务器管理权、公共环境和资产同样采用未来最小权限原则，不擅自收回现有权限。见 [服务器](SERVER.md) 与 [发布](RELEASE.md)。

## 环境、资源、启动与 CI

Python 项目使用 uv、pyproject.toml、uv.lock、Python 版本声明和 Ruff。共享大型仿真底座应版本化、独立任务包与个人环境隔离；个人安装绝不写入公共环境，公共环境运行不自动同步依赖。实际 GPU、显存、CPU、RAM、磁盘、耗时、预算与仿真版本应记录，未知标待测；不抢占他人资源。统一 run.sh doctor/smoke/reproduce/test/lint/ci。真实实验入口须实测，模板未配置时明确失败。CI 至少执行锁文件、Ruff lint/format、测试及软件 smoke；可移植 CPU CI 与 GPU/原生科研验收分开。见 [环境](ENVIRONMENT.md)、[资源](RESOURCES.md)、[CI](CI.md)。

## 验收与交接

科研证据记录 commit、环境、资产、配置、种子、Run ID、真实运行条件、指标及失败结果。区分 Mock、CPU、MuJoCo、PhysX 和实机；规划成功不等于导航成功，抓取成功不等于负载行走成功，端到端必须按任务合同验证同一连续过程。接手者能独立读懂现状、定位资源、运行检查、复现声明成果（无成功则明确未成功）、在个人工作区修改、测试和提交 PR。科研未完成也可诚实交接。AI 重要贡献应有真实溯源和验证依据。
